## Follow-up Docker CI failure

A subsequently supplied CI log confirms that the Linux amd64 image built successfully, including the production frontend/backend build. The runtime smoke test then timed out. Its test-only secret directory was mode 0700 and owned by the host runner, so the container's UID 1000 could not traverse the mounted directory to read its secrets.

The smoke test now mounts the two synthetic secret files individually and read-only, preserving the private host directory. Their test-only permissions are explicitly readable by the container regardless of the host umask. Production Compose already mounts individual secret files; its documented UID 1000 ownership and mode 0400 remain unchanged. The test also detects an exited container promptly, uses bounded readiness checks after startup and restart, and reports only safe state and fixed startup messages on failure.

The next supplied CI log confirms that the corrected container started and was healthy after restart, but the smoke test failed in its restart phase. The script retained the host port published before restart. Docker may reallocate an ephemeral host port on restart, as described in [Moby's Engine API documentation](https://github.com/moby/moby/blob/master/api/docs/v1.24.md). The smoke test now re-reads the loopback port mapping after restart and separately checks readiness, persisted setup state and administrator login.

The compiled application smoke test verifies file-based secrets and restarts the actual application process on a different backend port using the same database. It checks persisted administrator state, the existing session, CSRF-protected logout and a new login. The corrected Docker runtime smoke still needs a CI rerun: the local environment continues to lack an accessible Docker daemon. This correction is not recorded as a successful full container smoke test.
