# Contacts and communications

Communications are application-owned settings and metadata. They do not change Plex identity, grant library access, accept invitations, renew subscriptions or provide billing. Existing access management and backend monitoring remain separate. Configure SMTP in Notifications first and use only addresses you control for initial tests.

## Upgrade an existing installation

1. Take a consistent SQLite snapshot and a separate protected copy of the matching encryption key. Preserve the previous image tag/digest and runtime configuration. See [operations](operations.md).
2. Build or obtain the new amd64 image, replace runtime `APP_IMAGE`, and recreate the manager with the same data volume, encryption key and bootstrap file. No new environment variables or mounts are required. Never reset the database or generate a replacement encryption key.
3. Startup migrates schema 1 to schema 2 transactionally. Administrators, sessions, Plex/SMTP credentials, user notes, presets, expiries, incidents, audits and delivery history are preserved. A wrong key or failed migration stops startup; it does not claim success or partially commit the migration.
4. Existing standalone monitoring recipients retain outage/recovery behavior. They are labelled **administrator-provisioned; unverified**, with maintenance, announcement, welcome and expiry preferences initially off. They are not linked to Plex accounts or marked verified. Automatic welcome and expiry reminders default to disabled. Existing **access revocation expiries still execute**, including overdue work on startup.
5. Log in, check Users, Monitoring and Notifications, then open Communications. Review migrated contacts, integration status, failed dispatch jobs and SMTP acceptance history. Use a controlled SMTP test. Update the independently deployed external worker too if you want authenticated configuration comparisons.

Schema 2 cannot be opened by the previous schema-1 image. Rollback requires the pre-upgrade database snapshot, its matching encryption key and the old image. Runtime/Plex actions since that snapshot cannot be undone by restoring SQLite. Do not run both versions against one database.

## Notification contacts and recipient links

In Users, open a confirmed user and use **Notification contact**. Enter a separate email and explicitly choose the six independent categories: outage, recovery, maintenance, announcement, welcome and expiry. The account's stable Plex ID and selected server identify the contact. A Plex/invitation address is never automatically verified, and a pending invitation cannot be matched by display name or email. Wait until the confirmed account appears. Create standalone recipients in **Communications → Contacts**, or continue using Monitoring for administrator-provisioned outage/recovery recipients.

Saving an address does not verify it. **Queue recipient links** emails a 24-hour verification link and a separate 14-day preferences link. Opening either link changes nothing; the recipient must confirm an action. Verification is single-use and does not enable categories. Preference links remain usable until expiry, reissue, disabling the contact or changing its address. Reissuing invalidates earlier links of that scope. Address changes require administrator confirmation, invalidate that contact's links and reset verification of the destination address. Recipients can change categories and unsubscribe without becoming administrators or Plex users.

These are bearer links: anyone with the link can exercise only its email scope. Tokens are random, stored as hashes and carried in URL fragments rather than server-visible queries. The page removes the fragment before sending a same-origin POST; it keeps the token in memory only. Queue bodies containing links are encrypted with the deployment key, excluded from history responses and never cached by the service worker. A reload after fragment removal requires reopening the original email link. Do not forward links or post them in issues. Your HTTPS `PUBLIC_URL` must be reachable by intended recipients; otherwise self-service cannot work. No administrator login is needed on `/recipient`.

Generic communications are deduplicated by email address. Outage/recovery choices aggregate across active contacts; any address-wide unsubscribe or category opt-out takes precedence over administrator edits. Recipient preference changes apply to **all contacts at that address**. Different Plex users sharing an address cannot receive account-specific welcome or user expiry messages, to avoid leaking library/account information. Explicit administrator expiry/failure addresses are separate, administrator-controlled recipients. If the same eligible address has both user and administrator reminder roles, it receives one reminder. Address verification and consent are distinct. Already queued mail rechecks both before sending. Mail already accepted by SMTP cannot be recalled.

New linked contacts and new Contacts-screen recipients require verification. Existing standalone recipients, and recipients explicitly provisioned through Monitoring, retain administrator-controlled outage/recovery behavior without a fabricated verification claim. They must verify before receiving the new communication categories.

## Announcements

1. Open **Communications → Messages → New announcement**. Write a plain-text subject/body and choose all eligible contacts, selected Plex users or users currently accessing selected libraries. All includes eligible standalone contacts; user/library targeting excludes standalone recipients.
2. Save the draft. Optionally queue a test to an address you control; tests do not subscribe that address or send to the audience.
3. Choose **Preview recipients & content**. Review the rendered content, included addresses, exclusions and duplicate count. Unverified, inactive, unsubscribed, opted-out, pending or absent members are excluded. Preview tickets expire after five minutes and are invalidated by edits.
4. Leave the dispatch time blank for immediate queueing, or enter a future time **in UTC**. Confirm the exact audience and content. Confirmation fixes contact IDs, address revisions and share identity. New users are not added automatically.
5. Review History for dispatch and per-address SMTP status. Eligibility, preferences, address changes, membership and library targeting are rechecked before SMTP. A dispatch can contain suppressed recipients; **dispatched** means evaluated/queued, not delivered. Cancel a schedule or its remaining unsent deliveries; already accepted SMTP mail cannot be recalled. Delete only drafts; deleted drafts remain in audit/history. Queue failures can be retried explicitly, with current eligibility rechecked.

SMTP acceptance does not prove inbox delivery. Every recipient gets a separate message. Durable queue entries use stable Message-IDs and bounded retries, but SMTP cannot guarantee exactly-once delivery after an acceptance/disconnection or crash. Interrupted sends are retried with acceptance marked unknown. Provider limits, TLS errors and terminal failures remain visible.

## Maintenance events

Create an event in Messages with a title, explanation, selected affected server, UTC start/end, targeting and advance-notice leads in seconds. For example, `86400, 3600` means one day and one hour before start. Leave the leads empty for no advance notices; an event can be confirmed with zero recipients to provide suppression only. Preview and confirm the event before it takes effect.

Events and legacy Monitoring windows feed **the same suppression schedule**. Managed event windows appear read-only in Monitoring; edit their event in Communications. Overlapping windows continue suppression until all applicable windows end or are explicitly completed/cancelled. Cancel or extend an event to invalidate old unsent notices. You can optionally send a change, cancellation or completion notice to the original confirmed audience, rechecking current eligibility. An extended event may have a new advance notice under its new revision as well as a requested change notice.

Passing the expected end resumes ordinary monitoring. If an incident remains active, its unsent maintenance-suppressed outage can become eligible again; there is no repeated incident/email for already accepted notifications. If recovery occurred inside the window, old suppressed outage/recovery messages are not replayed as a catch-up burst. A planned end **never proves recovery** and never automatically sends a completion message. Use **Complete maintenance** only after checking the service yourself. That action and its email do not assert successful playback.

After a restart, only the latest due advance notice before the event start is eligible. Older missed leads and all notices whose start has already passed are superseded. Scheduled events, jobs, revisions and delivery state persist. The dashboard and Communications show expected-end-passed events until explicit completion/cancellation; prior events remain in history.

## Welcome messages

Configure templates, getting-started instructions, rules, request and support links in **Communications → Automation**. Allowlisted variables are `{{server}}`, `{{libraries}}`, `{{gettingStarted}}`, `{{rules}}`, `{{requestUrl}}` and `{{supportUrl}}`. Links must be public HTTPS URLs without credentials, queries or fragments; private/IP/admin application URLs are rejected. Keep free-text instructions appropriate for recipients and do not paste secrets or internal network information into them.

Automatic welcome is off by default. Enabling it does not welcome existing users. It requires an observed pending-to-accepted transition with the **same stable account and server-share IDs**, positive confirmed library access, a verified contact and welcome consent. The queue rechecks membership before sending. Each observed membership generation gets at most one automatic logical welcome. Observed absence followed by a new pending/accepted cycle with stable IDs creates a new generation. A changed invite/share/account ID, managed user, acceptance while the app was stopped or an already accepted baseline requires an explicit manual send; no matching by name or invitation email is attempted. This deliberately conservative behavior may skip many real Plex invitations whose identifiers change at acceptance.

Use the user editor to preview currently confirmed libraries, queue a test, or explicitly confirm send/resend to the eligible contact. A manual resend is intentional additional mail; retrying the same request ID does not create another entry. Inspect membership and delivery history. Editing automation settings supersedes pending welcome deliveries; an already queued automatic welcome is not silently resent with a different template. Use the explicit preview/resend if appropriate.

## Expiry reminders

Set a user's access expiry in the user editor, then separately enable reminders in Automation. Configure lead seconds, whether eligible user contacts receive reminders, administrator-controlled reminder/failure addresses, templates, instructions and an optional public renewal/request URL. Variables are `{{server}}`, `{{expires}}`, `{{instructions}}` and `{{renewalUrl}}`. Exact expiry times use ISO UTC. This is guidance for contacting the administrator; it never automatically renews access, charges money or promises renewal.

Reminder jobs track both expiry and settings revisions. Moving/removing an expiry or changing templates/preferences supersedes old unsent jobs; completed revocations and absent/pending memberships do not receive reminders. After downtime, only the latest due lead before expiry is eligible, avoiding a burst of old reminders. User messages require verified expiry consent and an unambiguous address. Administrator messages are individually delivered and identify the relevant account. If revocation fails or readback cannot confirm removal, only administrators receive a warning that access **may remain**. A unique warning is retained for that expiry revision rather than repeated for every retry.

Changing reminder settings does not cancel the access expiry itself. Overdue revocation continues independently of SMTP and communication scheduling. Settings changes supersede pending mail; accepted notifications with the same logical expiry/lead/role are not automatically recreated. Review failed expiry jobs in Monitoring before changing or rearming them.

## External worker and local limits

The NAS cannot send communications while its host, power or internet is unavailable. The independently provisioned [external worker](external-monitor.md) persists incidents and sends outage/recovery mail using its own database, recipients and SMTP, without contacting the offline NAS. It does not execute NAS announcements, welcome messages, expiry reminders or maintenance communications.

External configuration is **manual**, not automatically synchronised. Before a planned outage, copy the Communications maintenance export into the worker's private `monitor.maintenance`, update its recipient addresses/outage/recovery preferences separately, and restart it. The export contains windows and a digest, not secrets. Recipient changes/unsubscribes on the NAS must also be applied to the worker before relying on it. Both hosts use authenticated, nonce-bound acknowledgement digests to display matching, mismatched or unknown maintenance/recipient configuration. Missing acknowledgements from an old worker, offline workers and unauthenticated responses are never treated as a verified match. A successful heartbeat only proves receipt, not matching configuration. Check status freshness and apply edits while both hosts are reachable. New changes cannot reach an offline NAS or worker.

Select **External** notification authority to suppress local outage/recovery deliveries and avoid two senders for one failure. Provision and test worker SMTP/recipients before an outage; a webhook back to the NAS is not the email delivery mechanism. Local communications still use the local queue. Unknown gaps remain unknown and local health does not prove public playback.

## Troubleshooting and safe tests

Use synthetic accounts and controlled recipients for setup. Test drafts before confirming an audience, then schedule a near-future UTC announcement and cancel a second one. Create a short maintenance event with a controlled recipient, check suppression and optional cancellation/completion, and verify that time passing alone does not claim recovery. Use a disposable share for welcome/expiry live testing; mocked tests are not live Plex verification.

For missing mail, check SMTP, verified status, all six preferences, address-wide unsubscribe, confirmed membership, shared-address restrictions, scheduled UTC times, source integration status and suppressed/failed reasons. Unknown external configuration means it has not been authenticated; compare private worker settings and restart it. Save sensitive configuration only in runtime storage. Backups contain contacts, preference hashes, drafts and message content; protect them alongside credentials. See [security](../SECURITY.md) and [backup/restore](operations.md).
