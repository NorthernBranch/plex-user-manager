# Architecture

The React PWA is served with the API from the Node process. No build-time installation configuration enters the frontend. The production image contains compiled backend and frontend plus production dependencies, running as numeric UID/GID 1000 without capabilities.

| Module                                                                  | Responsibility                                                                                |
| ----------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| `server/auth.ts`                                                        | Bootstrap claiming, scrypt password hashing, rate limiting, sessions, same-origin/CSRF        |
| `server/config.ts`, `server/crypto.ts`                                  | Runtime schemas, file secrets and authenticated encryption                                    |
| `server/store.ts`                                                       | SQLite WAL, transactional migration, key validation, metadata and queue persistence           |
| `server/migrations.ts`                                                  | Transactional version-2 communications upgrade and standalone-recipient preservation          |
| `server/contacts.ts`, `server/recipients.ts`                            | Stable-ID contacts, address consent/verification, scoped hashed tokens and deduplication      |
| `server/communications.ts`, `server/communication-audience.ts`          | Draft/event services, confirmation snapshots, membership observation and audience eligibility |
| `server/communication-scheduler.ts`, `server/communication-delivery.ts` | Durable revision-aware jobs, bounded dispatch and delivery-time eligibility checks            |
| `server/communications-config.ts`, `server/maintenance.ts`              | Template/configuration schemas and shared effective suppression windows                       |
| `server/plex.ts`                                                        | Validated Plex account/PMS adapter, timeouts, safe errors, retry boundaries                   |
| `server/access.ts`                                                      | Per-server mutations, refresh/reconcile, bulk previews, persistent expiry execution           |
| `server/monitor.ts`                                                     | Incident state machine, timeline, logical notification creation                               |
| `server/email.ts`                                                       | Per-recipient SMTP queue, TLS, retries, stale and recovery ordering                           |
| `server/heartbeat.ts`, `server/external-monitor.ts`                     | Scoped signed heartbeats, replay checks, independent host detection                           |
| `server/index.ts`, `server/worker.ts`                                   | Separate local and external process lifecycles                                                |

Access operations are serialised within the process. Bulk preview records the selected server, share ID and before-state, expires in five minutes and is consumed once. Each user is refreshed before applying; externally changed shares are skipped. Mutation reconciliation can fail even after Plex accepted a request; the app reports that ambiguity rather than pretending to succeed. Expiry marks work running before calling Plex and re-fetches on restart: already-absent shares complete without a second deletion. Failures back off up to five attempts and remain visible.

Monitoring transitions healthy → suspected failure → confirmed outage → recovery pending → recovered. A failure during recovery keeps the existing incident. Short interruptions create no incident notification. Incidents and recipient jobs are created transactionally. A restart or excessive probe gap resets failure continuity; existing incidents remain open and downtime excludes unobserved intervals. The UI marks pre-probe state unknown. Observed downtime counts intervals following failing probes, not a claim about exact failure/playback duration.

Each delivery is unique by incident, kind and recipient. Recovery is ordered after an accepted outage to the same address, except for explicit recovery-only preferences. Pending/failed outage jobs are superseded at recovery. An outage already sending finishes first; failed uncertain acceptance is visible and can produce duplicates on retry. Recipient removal or opt-out suppresses queued messages before sending. Queue attempts use stable Message-IDs but do not guarantee deduplication by the SMTP provider. Five failed attempts produce a visible terminal failure; administrator retry is explicit, and stale outages cannot be retried. Probes, expiry processing, heartbeats and SMTP delivery use separate loops so a slow access or mail request cannot stall health observation.

Maintenance events and legacy windows share the effective suppression schedule. They suppress incident notifications and queued mail during the window. An ongoing incident's maintenance-suppressed unsent outage can become eligible when suppression ends; recovered incidents do not replay obsolete mail. Passing an expected end never confirms recovery or sends completion. The local queue suppresses outage/recovery delivery when external authority is selected. The external worker has independent configuration, encryption key and SQLite; it never queries the unavailable NAS for recipients or SMTP. Nonce-bound signed acknowledgement digests compare independently provisioned windows/recipients; no automatic configuration synchronisation occurs.

Communications use a separate non-overlapping ten-second scheduler, fresh validated Plex snapshots at least every thirty seconds and at most ten due dispatch jobs per tick. SMTP handles a configurable 1–20 messages per drain with one active drain and serial sends; health, expiry and heartbeat loops remain separate. Announcements retain the contact/address/share snapshot confirmed by an expiring preview ticket. Maintenance and expiry jobs have revisions, idempotent keys, latest-due catch-up and deadline checks. Queue delivery rechecks current consent, verification, address, event/expiry revision and confirmed membership. Failed source reads are not authoritative absence and trigger bounded retries.

Membership observation keys selected server and server-share ID, with the account ID checked before pending-to-accepted transitions. Existing accepted users are a baseline; reinvitation generations require observed absence. A changed share/account ID is never guessed from names/emails. Automatic logical welcome keys membership generation; explicit resends have separate request IDs. Contact tokens are stored only as hashes, expire by scope, and never establish an admin session. Link-bearing queue bodies are separately encrypted and omitted from API history. GET/navigation performs no preference mutation. Shared-address opt-outs take precedence, and personal messages are blocked for different Plex users sharing an address. See [the operational communications guide](communications.md).

One process must own each database; this is not an HA cluster. Sessions, contacts, drafts, email recipients, notes, audits and incident metadata are sensitive runtime data. Integration credentials and link-bearing private queue bodies are field-level encrypted. Use local-volume permissions, encrypted backup storage and TLS to protect the remainder. No production operation reads Plex media files.
